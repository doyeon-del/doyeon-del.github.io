과정 SSAFY 15기 특화 프로젝트 (블록체인 예측 도메인) 기간 2026.08 – 2026.10 팀 6인 · AI 파트(ML 모델·봇 서버) · 백엔드·프론트 연동 결과 SSAFY 우수 프로젝트 선정 (2026.10.02)

이번 주 실제 경주 목록과 말별 예측 확률 화면입니다. 화면의 점수와 확률은 제가 만든 예측 파이프라인에서 나옵니다.

프로젝트 개요

6개 항목의 비중을 조절하는 경마 예측

한국마사회 공공데이터 445,351행으로 학습한 모델이 말마다 컨디션·스피드·주행·기수·환경·실력 6개 항목 점수를 매기고, 사용자는 어떤 항목을 더 중시할지 비율만 정합니다. 과거 경주를 다시 푸는 게임이라 정답이 이미 있으므로, 예측과 베팅은 경주 전에 블록체인에 봉인합니다. 경마와 AI를 모두 모르는 2030을 위한 교육용·비환금성 서비스입니다.

1

결과를 보지 않는 예측

모델은 그 경주 이전 기록만 입력으로 받습니다.

2

재학습 없는 개인화

비율을 바꾸면 미리 계산한 항목별 점수를 가중합해 예측을 갱신합니다.

3

화면·베팅·정산의 확률 연동

화면 확률, 봇 베팅, 배당, 정산이 같은 숫자를 씁니다.

1주차에 기존 주제(포커·룰렛)의 한계를 짚고 경마 예측으로 재제안해 채택됐습니다. 위 세 조건은 그 기획안에서 정한 설계 요건입니다.

ML 모델 ① 문제 정의

경마를 분류가 아닌 랭킹 문제로 정의했습니다

말마다 1착 여부를 따로 맞히면 같은 경주 안의 상대가 누구인지가 빠집니다. 그래서 경주 안 순서를 맞히는 랭킹 문제로 보고, 6개 축마다 LightGBM lambdarank 모델을 따로 학습했습니다. 축 점수는 경주 안 백분위(0~100)로 내서, 화면과 봇이 같은 값을 씁니다.

  1. 피처는 전부 '그 경주 이전' 값

    경주성적 원본에서 피처 42개를 만들었고, 모두 해당 경주 전까지의 누적값입니다. 예측 대상 경주의 결과가 입력에 포함되지 않도록 했습니다.

  2. 미리 계산한 점수의 가중합

    축 점수를 미리 계산해 두면 사용자가 비율을 바꿀 때 가중합 한 번으로 예측이 바뀝니다. 요청마다 모델을 다시 학습하지 않도록 6개 축 점수를 선형 결합하는 방식을 사용했습니다.

  3. 슬라이더 조절 단위 결정

    슬라이더를 피처 42개에 붙일지 축 6개에 붙일지 정해지지 않아 화면과 서버 작업이 멈춰 있었습니다. 개별 피처의 비중 변경은 학습된 LightGBM 점수에 직접 반영하기 어려워, 미리 계산한 6개 축 점수를 조절하는 방식을 제안했습니다.

ML 모델 ② 확률 보정

랭킹 점수의 확률 변환과 보정

화면에는 "이 말이 1등 할 확률"이 나가고, 봇 베팅과 배당도 이 확률을 씁니다. 따라서 순위 예측과 함께, 예측 확률이 실제 적중 비율과 얼마나 차이 나는지 확인했습니다.

  • 축 결합은 Plackett-Luce로. 6개 축 점수를 Plackett-Luce 모형으로 선형 결합해 프리셋 가중치를 구했고, 단승·연승·복승 등 7가지 승식 확률은 1착 확률을 전개해 계산하는 기준 구현으로 만들었습니다.
  • 온도는 검증셋에서. 사용자 비율을 합 100으로 정규화하면 확률 분포가 평평해집니다. 이를 되돌리는 온도(T=0.0445)를 학습셋이 아닌 검증셋에서 맞췄습니다. 학습 데이터에 맞춘 보정값이 평가 결과를 낙관적으로 만들지 않도록 검증셋을 사용했습니다.
  • 결과. 검증 2,473경주에서 단승 예측 확률 평균 30.1%, 실제 적중률 29.8%를 기록했습니다.
함께 공개한 한계
2·3착으로 갈수록 예측 확률이 낙관적이었습니다(연승 예측 71.0%, 실측 59.5%). 보정을 마치지 못한 2·3착 확률은 순위 비교용으로 사용하도록 문서에 남겼습니다.

ML 모델 ③ 평가 기준

ML·DL 모델 비교와 학습 데이터 중복 수정

LightGBM은 제가, 딥러닝은 팀원이 만들었기 때문에 같은 기준이 없으면 어느 쪽이 나은지 말할 수 없었습니다. 분할·전처리·평가를 공통 코드 하나로 고정하고 규칙을 먼저 정했습니다.

  1. 테스트셋은 최종 1회만

    모델을 고르는 동안에는 검증셋만 씁니다.

  2. 오차 범위 안의 차이는 우열로 보지 않음

    표준오차(±0.85%p)의 2배보다 작은 차이는 같은 성능으로 봤습니다.

  3. 경주 단위 정렬을 매번 검사

    랭킹 모델은 경주 순서가 깨져도 에러 없이 틀린 모델이 나오므로, 데이터를 불러올 때마다 확인했습니다.

기준선 (검증 1,254경주)1착 적중
LightGBM (배당 제외 73피처)34.0%
시장 1번 인기마39.3%

성능은 절대 적중률이 아니라 무작위·시장 대비로 말하도록 기준선을 함께 세웠습니다. 이 기준으로 팀원의 딥러닝 4개 구조도 비교했고, LightGBM과의 적중률 차이가 정한 비교 기준의 오차 범위 안에 있었습니다.

ML 모델 ④ 프리셋

프리셋별 계수 설정과 예측 결과

프리셋은 적중률과 선택한 말의 배당 수준에 따라 예측 성향을 고르는 기능으로 설계했습니다. 배당형·역배형 프리셋의 시장 계수는 서버의 결합식을 그대로 옮겨 최우도로 적합했습니다.

서비스 연결

예측 확률을 활용한 봇 베팅과 정산

사용자가 함께 예측을 겨룰 봇 9명의 베팅 로직을 구현했습니다. 모델이 계산한 확률에 따라 말을 선택하되, 봇마다 적중률이 달라지고 배당이 상한을 넘지 않도록 조정했습니다.

봇의 베팅만으로 배당을 조절하기 어려웠습니다

게임용 1,166경주로 시뮬레이션한 결과, 출전 두수에 따라 배당 상한이 달라 고정된 베팅 비율로는 대응하기 어려웠습니다. 봇 강도를 조절하는 값도 말의 선택 순서를 바꾸지 못해 적중률 차이가 나지 않았습니다.

배당 조절과 봇의 말 선택을 분리했습니다

배당 상한에 필요한 자금은 별도로 계산하고, 봇은 모델 확률에 따라 말을 선택하도록 바꿨습니다. 변경 후 시뮬레이션 270회에서 상한 위반은 없었고, 봇별 적중률은 12~38%, 수익률은 −8~−20%였습니다.

  • 베팅 API 구현. 봇의 말 선택 로직을 FastAPI로 제공했습니다. 같은 방과 봇에 대한 결과 재현, 요청 데이터에 경주 결과가 포함되지 않는지 등을 pytest 테스트 90건으로 확인했습니다.
  • 게임용 경주 적재. 축 점수를 1,140경주 분량으로 내보내 백엔드가 기동 시 적재하게 했습니다. 표시용 지표가 섞이면 1착 적중이 4.6%p 떨어지는 것을 확인하고 축 점수만 읽게 했습니다.
  • 정산 오류 수정. 마사회 실제 확정 배당으로 정산 식을 검증해, 연승 정산이 베팅 총액의 240%까지 지급되던 오류(입상 두수 나눗셈 누락)를 찾아 고쳤습니다.
  • 배당 1.0배 문제. 배포 서버에서 직접 플레이하다 연승 배당이 1.0배로 깔리는 것을 발견했습니다. 원인은 봇의 인기마 집중(0.6)이었고, 인기마 집중 값을 0.3~0.4로 낮추는 수정안을 제안했습니다.

작업을 돌아보며

모델 평가 외에도 봇 베팅과 정산을 점검하면서 학습 데이터 중복과 배당 계산 오류를 발견했습니다. 예측 결과를 서비스에 붙이는 과정에서 데이터 적재, 봇 동작, 정산 식까지 함께 수정해야 했습니다.
