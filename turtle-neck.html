서비스 웹캠 기반 실시간 자세 감지·스트레칭 데스크톱 앱 결과 SSAFY 우수 프로젝트 선정 (2026.08) · 가입 사용자 80여 명 팀 5인 · 팀장·FE 전담

지표 정의

홈과 기록 화면의 연속 기록 숫자가 달랐습니다

사용자 테스트에서 같은 사용자의 연속 기록이 화면마다 다르게 표시된다는 피드백을 받았습니다. 화면의 계산 기준과 서버의 집계 기준이 달랐던 것이 원인이었고, 지표 정의를 팀에서 합의해 맞췄습니다.

  1. 기록 불일치 발견

    홈의 연속 기록과 내 기록 화면의 연속 기록이 서로 다른 숫자를 보여줬습니다. 어느 쪽이 맞는지 판단할 정의가 문서에 없었습니다.

  2. 원인 분해

    화면 계산과 서버 집계가 갈리는 지점을 네 갈래로 나눠 추적했습니다. '바른 자세 시간'을 어떤 값(workSeconds vs effectiveMonitoringSeconds)으로 셀지가 화면과 서버에서 달랐다는 것을 확인했습니다.

  3. 지표 정의 합의

    팀원들과 연속 기록의 정의와 계산 기준을 하나로 합의하고 문서로 남겼습니다. 이후 새로 만드는 화면도 같은 정의를 따르게 했습니다.

  4. 담당자별 반영

    프론트엔드 화면 계산은 직접 수정했고, 서버 집계는 합의한 정의를 백엔드 담당자에게 전달해 수정 결과를 함께 확인했습니다. 이후 모든 화면이 같은 숫자를 보여줍니다.

주요 기능

  1. 실시간 자세 감지

    거북목(구부정한 자세)·화면 근접·졸음 3가지 상태를 웹캠으로 실시간 감지하고 화면 알림으로 알려줍니다. 시스템 트레이에 상주해 창을 닫아도 백그라운드에서 감지가 이어지며, 모든 영상 분석은 사용자 PC 안에서만 이루어지고 영상은 서버로 전송되지 않습니다.

  2. 스트레칭 가이드 및 동작 판정

    설정한 작업 시간이 끝나면 스트레칭을 제안하고, 동작별 상세 가이드에 따라 올바르게 수행했는지 카메라로 판정합니다.

  3. 개인 / 팀 모드

    혼자서도, 팀 단위로도 사용할 수 있습니다. 팀 모드에서는 서로의 작업 상태를 공유하고, 팀에서 정한 시각에 팀원들과 같이 스트레칭합니다.

  4. 보상 / 상점

    세션 참여와 좋은 자세 유지로 골드를 받아 캐릭터를 꾸밉니다. 키운 캐릭터는 트레이 아이콘에도 표시됩니다.

  5. 기록 대시보드

    개인 단위로도, 팀 단위로도 바른 자세 시간, 시간대별 그래프, 연속 기록을 확인할 수 있습니다.

핵심 기술

온디바이스 AI

MediaPipe(Face/Pose Landmarker)를 서버가 아닌 사용자 PC의 렌더러에서 직접 실행합니다. 웹캠 영상은 PC 밖으로 나가지 않고, 서버에는 집계 결과만 전송됩니다.

개인화 캘리브레이션

목-어깨 비율의 절대값은 사람·카메라 위치마다 달라 고정 임계값으로는 판정할 수 없습니다. 시작 시 사용자의 "바른 자세"를 측정해 개인 baseline을 만들고 기준 대비 하락률(%)로 판정하며, 어깨가 화면 밖으로 나가는 상황 감지 같은 환경 점검까지 포함해 오판정을 줄였습니다. 임계값 근처에서 판정이 깜빡이지 않도록 히스테리시스·지속시간 확정 로직도 둡니다.

스트레칭 동작 채점

관절 각도 기반으로 진행률·축 이탈·측정 불가를 분리해 채점하고, 조건별 진행률 중 최솟값을 써서 모든 조건을 만족해야 동작이 인정되게 했습니다. 판정 로직은 웹캠 없이 실행되는 순수 함수와 상태 머신으로 만들어 유닛 테스트 22종으로 확인했습니다.

팀 세션 실시간 동기화

WebSocket으로 팀원 간 작업 상태 공유와 동시 스트레칭 세션을 구현했습니다. STOMP를 쓰지 않고 필요한 메시지만 담은 JSON 형식을 직접 정했습니다.

시스템 아키텍처

영상은 PC에서 처리하고, 서버에는 세션 기록 1건만 보냅니다

AI 문서 혼선

AI가 만든 문서가 늘수록 혼란도 늘었습니다

팀원 각자가 생성형 AI로 산출물을 만들자, 같은 기능을 서로 다르게 이해하는 일이 생겼습니다. 같은 질문에도 시점·사람·모델에 따라 AI의 답이 달라졌고, 문서끼리 서로 충돌했습니다. 그래서 팀장으로서 기준 문서부터 정했습니다.

AI 모듈 지연

AI 모듈이 완성되기 전에 나머지를 먼저 완성했습니다

감지 엔진(MediaPipe)의 완성이 늦어지면 알림·세션 등 프론트 전체가 대기해야 하는 일정 위험이 있었습니다. 그래서 결과 타입부터 합의하고, 나머지를 동시에 개발했습니다.

  1. 감지 결과 타입만 계약으로 정의

    MediaPipe 감지 엔진이 완성되기 전에, 그 출력 타입부터 팀 계약으로 고정했습니다.

  2. 시뮬레이터로 알림·세션 로직 먼저 완성

    계약된 타입을 대신 생성하는 시뮬레이터로 알림과 세션 로직을 먼저 개발했습니다.

  3. 알림 규칙은 순수 함수로 분리해 테스트 40건

    세션 18건·알림 22건의 테스트로 계약이 지켜지는지 확인했습니다.

  4. AI 모듈 투입 시 알림 코드 무수정

    실제 감지 엔진이 들어왔을 때 알림 코드는 수정 없이 그대로 동작했습니다.

배운 점과 개선 방향

팀장으로서 개발 기준을 먼저 정했습니다. 화면과 서버의 숫자가 달랐을 때도 코드를 고치기 전에 지표 정의부터 합의했습니다. 기준 문서와 타입 계약을 정해 두니 다섯 명이 나눠 작업해도 결과를 하나로 합칠 수 있었습니다.

아쉬운 점과 개선 방향

  • 서버를 EC2 한 대에 모두 올려, 서버가 멈추면 서비스 전체가 멈추는 구조입니다. DB를 RDS로 분리하고 백업을 자동화하는 것이 우선 과제입니다.
  • Jenkins가 운영 서버에서 직접 이미지를 빌드해 배포할 때마다 서버에 부하가 생깁니다. 빌드를 분리하고 이미지 저장소(ECR)에서 받아 배포하는 방식으로 바꾸고 싶습니다.
  • 감지 모델 파일을 처음 쓸 때 CDN에서 내려받아, 첫 감지에는 인터넷 연결이 필요합니다. 모델을 앱에 포함하면 오프라인에서도 바로 쓸 수 있습니다.
  • '총 작업 시간'으로 보이던 값이 실제로는 자세 측정 시간이었습니다. 작업 시간을 따로 집계하지 못하고 화면 이름을 '자세 시간'으로 바꿔 대응했습니다.
